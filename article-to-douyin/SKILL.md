# article-to-douyin · 文章转抖音图文

## 这个 skill 解决什么

输入一篇 AI / 科技类文章（也兼容其他领域），输出一套可直接上传的抖音图文：
3:4 卡片 PNG、首行候选、完整文案、话题，以及一个汇总单文件 HTML。

**不包含自动发布。** 发布走抖音 App 的图文入口，由用户手动确认。
原因是抖音官方发布接口要求企业主体且逐项审核，非官方自动化会封号，
详见 `references/why-no-autopublish.md`。

> **若用户要求做本机半自动发布**（已验证可跑通）：
> **用夸克本体跑**（`launchPersistentContext` + `executablePath` 指向 `quark.exe`），
> 直接复用夸克自己的登录态 → 自动上传 + 填标题/描述/话题/自主声明 → **停在发布页**。
> ⚠️ **不要跨浏览器搬 Cookie** —— 登录态在哪个浏览器里，就用哪个浏览器跑（用户明确要求）。
> 完整实现细节、profile 副本的组装方法、两个发布页的区分、以及必踩的坑，见
> `references/publish-automation-quark.md`。**绝不自动点「发布」。**

**小红书是另一套流程**（文案长度、图片比例、话题玩法都不同），见 `article-to-xhs`，
不要在本次流程里顺带产出小红书内容，两套混做容易互相污染。

## 抖音与小红书的五点本质差异（先读这个，否则会做废）

| 维度 | 小红书 | **抖音图文** |
|---|---|---|
| **核心指标** | 完读率 / 收藏 | **「划到最后一张」的比例** —— 图文没有完播率 |
| **第 2 张的作用** | 承接叙事 | **必须独立成立**。第 2 张决定他要不要划第 3 张；若只是第 1 张的补充说明，这条就到头了 |
| **内容编排** | 按叙事顺序 | **排序本身就是核心工作**。同样 9 张图，换个顺序数据能差好几倍 |
| **流量来源** | 推荐为主 | **推荐 ≈70% + 搜索 ≈30%**，图文天然更利于被搜索抓到 |
| **话题结构** | 短尾 + 场景词；**总数 ≤5 个** | **三级结构**：泛流量大标签 + 垂直领域标签 + 地域/热点标签；**总数 ≤5 个** |
| **评论区** | 一般权重 | **权重极高**，文案与末页必须埋争议点或开放提问 |
| **合规** | 无强制标注 | **「自主声明」固定选「内容由AI生成」，由脚本代选**（2026-10-05 用户更新；此前的「无需添加自主声明」已作废） |

**一句话记忆：小红书是「读」，抖音是「划」。** 做抖音图文的真功夫在排序，不在文笔。

## 执行流程（九个环节）

```
⓪ 选题发现 → ① 输入 → ② 提纯 → ③ 事实核验 → ④ 结构重组 → ⑤ 改写 → ⑥ 出图 → ⑦ 汇总HTML → ⑧ 刷新总索引
   全自动 ──────────────────────────────────────────────┘                      ↓
                                                                    人工：抖音 App 发布
```

### ⓪ 选题发现（用户说「今天发什么」「帮我找点素材」「跑选题发现」时执行）

#### 🚧 与「常规热榜」严格分离（用户 2026-09-29 明确要求）

**本环节产出的是「AI 科技选题池」，不是「今日热榜」。两者必须分开，不得混在一份文件里。**

| 属于本池（用） | 不属于本池（不用） |
|---|---|
| **抖音总榜**（作品榜，带播放量）—— 本 skill 的独占源 | **抖音热搜（话题榜）**、微博 / 百度 / B站 / 快手热搜 |
| 今日热榜的**科技 / AI 分类节点**（媒体源，带原始链接与热度） | 影视票房、音乐榜、App Store 榜、报纸版面 |
| **X 聚合站**（境外 AI 前沿，二手转载需回一手核） | 任何「社会话题榜」「吃瓜榜」 |
| Hacker News / Reddit / **GitHub Trending** | — |

⚠️ **「抖音总榜」和「抖音热搜」在今日热榜里是两个不同节点，别混。**
总榜是作品榜（带播放量），热搜是话题榜。本 skill 只用总榜。

理由（用户原话的意思）：常规热榜是「今天大家在聊什么」，跟账号的 AI / 科技定位错配，
混进来只会把选题池稀释掉。**要看常规热榜就单独出一份，别合并。**

#### 🚧 选题不看用户背景（用户 2026-10-01 明确要求）

**做选题发现时，不要把用户的个人背景、职业经历、以往内容方向当作筛选或加权因素。**

- ❌ 不做「这个跟他以前的经历有关，优先给他」
- ❌ 不做「这不在他的舒适区 / 他没做过这个方向，略过」
- ✅ 只按内容本身判：**此刻热度 + 可做度 + 与账号 AI/科技定位是否匹配**

> 与「发布前查重」不冲突：查 `C:\小红书\` / `C:\抖音\` 已有目录、同一事件做过就 pass，
> 是用户单独提出的硬规则，**继续执行**。本条取消的是**选题阶段的个人化加权**，不是成稿前的去重。

#### 触发方式（用户视角：只需要说一句话）

| 你想干什么 | 直接说这句 |
|---|---|
| **标准（推荐，双平台一次出）** | `跑选题发现：小红书和抖音各一份，只用 AI/科技源，常规热榜别混进来。` |
| 最简（全用默认） | `跑选题发现` |
| 只做抖音 | `跑选题发现，只做抖音` |
| 多要能蹭的即时热点 | `跑选题发现，多给我能蹭即时热点的（新品发布/融资/榜单），少来观点文` |
| 限定条数 | `跑选题发现，给我 12 条左右，按可做度排序` |
| 顺带也要常规热榜 | `跑选题发现；常规热榜另外单独出一份，别和选题池合并` |

**上面任选一句即可，不需要复述下面的规范。**

> ⚠️ 下面这份是**执行规范，写给 AI 看的，用户无需念出来**：

```
跑一遍抖音选题发现：
1) 源用：抖音总榜（tophub 节点）+ 今日热榜科技/AI 节点 + X 聚合站 + GitHub Trending；
2) 常规热榜（微博/百度/B站/快手热搜、抖音热搜）不要混进来；
3) 同一条被多源命中的合并成一条，标出命中源数量；
4) 每条给出：标题 / 命中源 / 数据证据 / 可做角度 / 首行候选（≤20 字）/
   三级话题结构（泛流量+垂直+地域或热点）/「第 2 张放什么」；
5) 单源条目单独标「单源待核」；
6) 采不到的源如实写在末尾并写明原因，不要跳过、不要用推测补；
7) 产出单文件 HTML，存到 C:\抖音\选题\今日AI科技选题池_<日期>.html。
```

### ① 输入：拿到干净正文

按顺序尝试，成功即停：

1. **WebFetch 直接抓**（首选，36氪、机器之心、量子位、知乎、掘金、tophub 等大多数站点直接可读）
2. **本机 Playwright 抓取**（Chromium 已装好，见下文环境路径），用于第 1 步失败的场景
3. **用户粘贴的原文**：直接使用，零风险

**Jina Reader 已不可当免费降级用。** 2026-09-28 实测，`https://r.jina.ai/{URL}` 对
**任意** URL（含 `example.com`）一律返回 **403**，需自行申请 API Key。

**已知硬骨头：微信公众号文章。** 普通抓取会被中断，直接向用户要正文，不要反复重试。

抓取时要求：保留小标题、全部数字、公司名 / 产品名 / 人名、引用原话。**不要让它总结。**

### ② 提纯：抽出事实内核

从正文里抽出结构化的事实清单：数字、版本号、机构名、时间点、结论、争议点。
逐条与原文对齐，**不得漂移、不得外推、不得补全原文没说的因果关系**。

### ③ 事实核验（必做，不可跳过）

**这一步是本 skill 与普通「一键生成」工具的核心差别。**

用 WebSearch 对事实内核里的关键点做交叉检索，按三级标注：

| 级别 | 判定标准 | 处理方式 |
|---|---|---|
| **L1 共识** | ≥3 个独立来源一致，或官方直接发布 | 正文正常写，**不必逐条标来源** |
| **L2 据报道** | 1–2 个可信媒体来源 | 正文用「据报道」「XX 称」，一句带过 |
| **L3 爆料 / 传闻** | 社交媒体、单一匿名源、泄露截图、厂商自述 | **必须显式标注「未经官方确认」**，且不能写进首行当标题 |

同时必须做的三件事：

- **找反方。** 至少检索一次「质疑 / 反驳 / 不能证伪 / 未经验证」这一侧。
- **修正原文的绝对化表述。** 「碾压」「彻底告别」这类词在核验后若缺支撑，降级为「在这组测试中超过」。
- **写清分歧。** 多来源矛盾时**并列写出**，不要挑一个当定论，也不要取平均。

核验结果落成一张表（信息点 / 来源数 / 级别 / 备注），放进 ⑦ 的汇总 HTML。
判断标准见 `references/fact-check.md`。

**⚠️ 选题池里的判断，出成品前必须逐条回搜验证（2026-09-30 踩坑）**

从 ⓪ 选题发现产出的池子里挑条目时，池子里写的「数字」和「落差 / 冲突」是**当时的快速判断**，
不是已核验结论。进 ③ 时必须把它们当**待验证的假设**，不能直接抄。实测踩到的两类坑：

1. **数字被记错**：池子写「缓存输入价从 $1 降到 $0.10」，核验后实为 **$0.20 → $0.10**
   —— 错因是把同批新闻里两个型号的缓存价串了行。
2. **「落差」是编出来的**：池子写「国内标题写成『因新模型太强叫停发布』」，
   回搜后**找不到任何一篇国内标题作此表述**。整条内容原本靠这个落差立住，
   不验证直接写，等于替读者编了一个因果。

原则：池子里的每个**具体数字**都要回一手源核一遍；每个**口径分歧 / 反差**必须能指名到
具体来源的具体表述。**验证不通过就换角度，不要为了让内容好看而保留。**
换角度的示例：把「国内标题说太强」换成可验证的「跑分 98%/99.9%/100%，却因可靠性不达标被按下」
—— 张力还在，但每句都能核。

### ④ 结构重组（**排序优先，与小红书不同**）

**不要顺着原文的段落顺序改写。** 按三步走：

1. **拆**：把 ② 的事实内核拆成彼此独立的信息点，脱离原文叙事顺序
2. **重排**：**这一步对抖音是决定性的。** 两个硬约束：
   - **第 2 张必须独立成立**，且要有第 1 张没有的新信息。若第 2 张只是第 1 张的补充说明，整条就到头了
   - **每张都要能单独看懂**——用户可能从任意一张滑入，也可能只看 2–3 张就走
3. **重述**：换句式而不只是换词；连接词改口语方向；段落长短打散

选阅读骨架（骨架不得沿用原文的）：

- **结论先行**（评测、数据类）→ **对比反转**（争议、辟谣类）→ **时间线**（事件演进）
- **问答**（高密度干货）→ **数字拆解**（单点数据冲击）

**重制的底气来自「信息增量」**——③ 核验查出的版本时点、反方声音、口径分歧、
原文里对自己不利的平衡信息，都是原文没有的内容，这才是与洗稿的分水岭。
**若找不到 2 条原文没有的信息，说明 ③ 没做透，回去补查。**

自检四问见 `references/rewrite-structure.md`。

### ⑤ 改写：抖音口吻

**抖音没有独立标题字段——文案的第一行就是标题。** 这一条决定改写的起点。

- **首行即标题**：**硬限 ≤20 字**，制造信息缺口（「但我必须说个真相」这类），
  不要「今天我们来聊聊」
- **前 3 行定生死**：信息流只外露前 3 行（约 55 字），第 1 行冲突、第 2 行共鸣、第 3 行给承诺
- **正文硬限 ≤1000 字**（目标 600–900）。图文（多图滑动）建议 **600–900 字**——
  图文读者愿意往下翻，关键是**每段 ≤3 行**，不是把话砍短。

> ⚠️ **2026-09-29 末次更正，两平台口径已统一为「标题 20 / 正文 1000」，都是硬规则。**
> 中途曾按「抖音标题 ≤35 字、正文建议 1000、底线 2000」放宽过一轮，用户随后更正：
> 「**字数限制是我错了，两边都是标题 20 字，正文 1000 字**，你就按照这个规则执行吧。」
> 原先记在这里的「35 字 vs 图文页计数器 19/20」冲突**就此消解**——图文页实测上限本就是 20 字，
> 与用户的最终口径一致。视频页标题框是 30 字，但**本项目按 20 字执行，不留例外**。
> 出处：本机创作者中心后台 dump（图文页计数器 `19/20`）+ 用户 2026-09-29 最终确认。
- **话题最多 5 个 —— 硬规则（2026-09-30 用户明确）**。用户原话：「**话题最多带 5 个，
  小红书和抖音都是一样的，超过 5 个的你删掉**」。超了就删尾部的泛流量词，
  保留最贴内容的前 5 个，别再按 7 个出稿。脚本 `check_copy.py` 会报话题个数。
- **正文用 emoji 做小标题分段**（与小红书同源写法）：开场 1–2 段纯文字 → 3–5 个
  「🐰 小标题」段落 → 结尾一句号召 + 一个提问。emoji 只在段首，不要每句都塞
- **每段 ≤3 行**，关键信息单独成段
- **埋争议点**：评论区权重极高（有运营复盘称评论权重高于点赞），文案里要留一个能吵起来的点
- **结尾开放式提问**：「你觉得这算合格吗？评论区说」，不要「点赞关注」式硬广
- **读者索要链接 / 资源时，话术统一写「要的，评论区留言」**（2026-09-29 用户明确）——
  不要再加说明性长句，也不写「私信发你」
- 英文技术术语（Token、Agent、Prompt）保留原文，不硬翻
- 去 AI 味：删掉「值得注意的是」「综上所述」「不仅…而且…」
- **产品 / 主题名一律用中文**（型号名可保留英文，如「Gemini 4 Pro」）

首行给 3 版候选：悬念型 / 冲突型 / 数字型。

### ⑥ 出图

- **张数上限 35 张**（抖音图文上传上限，用户 2026-09-29 明确给出）。

  **叙事型图文**仍建议 4–9 张——少于 4 张撑不起内容，超过 9 张完读率会掉。

- 封面深色抓点击，内页浅底深字保阅读舒适度

#### 抖音特有的三处结构（模板已内置，改写时不要抹掉）

1. **连号页码** `01/09`：让读者知道总量和进度，直接影响「划到最后一张」的意愿
2. **封面底部滑动提示**「左滑看完全部 9 张」：抖音是滑动交互，要明示
3. **末页底部双行**：左边来源、右边互动引导（抖音评论权重高）

#### 单页信息量比小红书更少，字号更大

| 元素 | 小红书 | **抖音** |
|---|---|---|
| 内页标题 `.in-title` | 62px | **68px** |
| 条目标题 `.item-t` | 33px | **36px** |
| 条目正文 `.item-d` | 27px | **29px** |

**排版密度（2026-09-28 实测得出，务必照做）：**

**先用 `scripts/check_density.py` 量化测一遍**，别靠肉眼估：

```bash
"$PY" "$SKILL/scripts/check_density.py" --cards '<output 目录绝对路径>'
```

它会逐张输出 `bottom_blank`（底部留白比例），并统计 `LOW_COUNT`。
**目标：底部留白控制在 15–24%。超过 25% 就是「没做完」的观感。**

实测出来的 gap 参考值（3:4，1080×1440 版面）：

| 版式 | gap | 实测底部留白 |
|---|---|---|
| 4 条 `item` | **44px** | 15.6% |
| 5 条 `point` | **60–70px** | 15.0–21.4% |
| 2 `point` + 榜单表 | **40px** | 24.4% |
| 3 `point` + 数据块 | **44px** | 18.3% |

**留白超标的正确做法是「补内容」，不是继续拉大 gap。** 间距超过 70px 视觉就散了。
补的内容**必须是已核验过的信息点**——通常是 ② 提纯时为求简洁砍掉的条目，
重新补回来即可。**不允许为了填满而编造、外推或注水。**

本次实测：02/04/06/07/08 五页初始留白 25–36%，各补 1 条已核验信息 + 调大 gap 后，
全部回到 15–22%。

⚠️ **两类页的读数是固定值，不能按阈值判断，直接忽略**：

- **封面**：三段 `space-between` 布局，`cv-foot`（数据 + 滑动提示）本来就贴底，
  读数稳在 0–6%，与内容多少无关；
- **带 `.in-foot` 的末页**：脚注绝对定位在 `bottom:72px`，读数**恒为 5% 上下**，
  不管内容是 3 条还是 5 条都一样。

这两类页只能靠**肉眼**看内容与脚注之间有没有过大空隙（空隙超过 25% 就补一条）。

⚠️ **过满同样要处理**：2026-09-29 实测有一页补到 `bottom_blank=0.3%`（填充 99.7%），
虽未裁切但已无呼吸感。**目标区间是填充 75–90%，超过 95% 要回撤一条内容**，
不要一路补到底。**

#### 来源标注与合规

- **封面不要放来源，也不要放日期**。左上角只放分类 chip（如「AI 前沿」），右上角只放**连号页码**。
  > ⚠️ 右上角是页码，不是日期 —— 用户 2026-09-29 明确「封面不写日期，我可能会提前做」。
- **封面大字的单行容量上限（2026-09-30 实测）**：`cv-title` 与 `cv-title2` 均为
  `font-size:118px`，内容宽 904px → **一行最多约 7 个汉字**，8 字会换行挤乱封面。
  中英混排可放宽（`GPT-6.1 Sol` 这类拉丁字符较窄，11 个字符仍占一行）。
  出图后**必须回看封面 PNG 确认没有换行**。
- **封面大字必须出现具体主体名（用户 2026-09-30 反馈，硬要求）**。
  事件型 / 新品型选题，封面若只有「取消发布 / 因为它不诚实」这类判断句，
  读者划到封面不知道说的是谁。要求：
  - `cv-title` 或 `cv-title2` 至少一行带出**模型名 / 产品名**（如 `Astra 取消发布`）；
  - 公司名放 kicker（如 `OpenAI 大会前夜`），不占用大字位；
  - 判断句、情绪词保留在第二行当钩子，但第一行必须先交代主体。
- 实测字号：第一行写成「拉丁模型名 + 4 个汉字」时收到 `100px` 更稳
  → `style="font-size:100px;letter-spacing:-1px"`，第二行保持 118px，
  两行视觉宽度接近，比整页统一字号更齐。
- **来源统一放在最后一页底部，且只写一行媒体名**：

  ```

  ```

  **不要附加原标题、日期、免责说明。**
- 未证实内容（L3）的「未经官方确认」警示照常放在对应的内容页页首（琥珀色警示框）。
- 末页底部右侧留一行**互动引导**（如「你觉得这波能信几成？」）。
- **末页加脚注会挤压内容高度**：双行脚注约 58px，配 `gap:44px` 刚好。改完必须肉眼复核末页。

用来读 PNG 算底部留白，其余全部为标准库；Node 侧只需要 `playwright-core` + 一个 Chromium。

**跨设备覆盖方式**（都不需要改代码、也不需要改本文件）：

| 要覆盖什么 | 环境变量 | 说明 |
|---|---|---|
| Node 可执行文件 | `NODE_BIN` | 仅在 node 不在 PATH 时用；`env_check.py` 会读它 |
| playwright-core 位置 | `NODE_PATH` | 指向含 `playwright-core` 的 `node_modules` |
| Chromium | `PW_CHROMIUM` / `PLAYWRIGHT_BROWSERS_PATH` | 前者指可执行文件，后者指浏览器根目录 |
| 成品目录 | `XHS_DIR` / `DY_DIR` | 也可在 skill 目录放 `config.json`（见 `build_index.py` 头部） |

**不要 `pip install` 或 `npm install -g`**，所有依赖已在隔离目录内。

换到全新环境（例如云端 Linux 沙箱）时，按自检输出的缺失项补装即可：
`npx playwright install chromium`；中文字体缺了中文会渲染成方块，Debian 系装 `fonts-noto-cjk`。

## 输出位置与结构

**最终交付物统一放到「抖音成品根目录」**（本机为 `C:\抖音`，与小红书根目录平行，用途相同：
方便查找和上传）。该根目录**可配置**：设 `DY_DIR` 环境变量，或在 **`article-to-xhs`** skill
目录下建 `config.json` 写 `"dy_dir"`（两个 skill 成对安装、共用一份配置；**配置放 douyin 目录下
不会被读取**，因为扫描与索引逻辑都在 xhs 侧）。换设备 / 上云端时改这里即可，**不必改本文件**。

```
<抖音根目录>\
├── 选题\
│   └── 今日AI科技选题池_<日期>.html      # 抓取的选题清单
└── <YYYYMMDD>_<中文主题>\                 # 每条图文一个独立子文件夹
    ├── 抖音_<中文主题>.html               # 交付主件：单文件、图片 base64 内嵌
    ├── 01-封面.png
    ├── 02-xxx.png
    └── ...                               # 文件名顺序即上传顺序
```

**目录约定：**

- **每条图文新建一个独立子文件夹**，PNG **和** 汇总 HTML 都放进去。
- 文件夹名格式：`<YYYYMMDD>_<中文主题>`。
- **所有抓取来的资料（选题池、榜单清单）统一放进 `选题\`**。
- 构建过程文件（cards.html、meta.json、渲染脚本副本、临时日志）留在工作区，**不要混进交付目录**。
- **不要单独产出 `发布文案.md`** —— 文案已在汇总 HTML 的一键复制区里。

文件名与卡片标题**一律用中文**。

## 发布（第 5 环节，人工操作）

0. **先过违禁词自检**（见「四项自检」第 4 项）。有高危词先改、**重出受影响卡片、重新生成汇总页**。
   若走「本机半自动助手」（`pub_fill.cjs`），**脚本已内置这道闸**：读完 `_发布内容.json`
   先跑离线检测，**高危词直接中止（退出码 2），浏览器都不会打开**；中危词打印警告后继续。
   词库在 `C:\抖音\发布助手\banned_words.json`，要跳过得显式设 `PUB_SKIP_WORDCHECK=1`。
1. 打开抖音 App，点底部「+」号
2. 顶部标签栏选「图文」（若无此标签，先升级 App 至最新正式版）
3. 按 `01` → `0N` 顺序上传全部图片（图文上限 35 张）
4. **「自主声明」固定选「内容由AI生成」，由脚本代选**（2026-10-05 用户更新）。
   控件路径：页面上「自主声明」入口 → 弹层「对作品内容添加声明」→ 单选「内容由AI生成」→ 确定。
   该控件共 6 个选项（内容由AI生成 / 内容为个人观点或见解 / 内容为转载信息 /
   内容含营销推广信息 / 虚构演绎，仅供娱乐 / 无需添加自主声明）。
   ⚠️ 2026-09-29 曾定「不代操作、保持页面默认」，**已被本条覆盖**，不要再改回去。
5. 打开右上角齿轮里的「高清发布」开关（否则会被压到 720p）
6. **文案用汇总页的「一键复制全文」按钮复制**（2026-09-29 新增）——**抖音编辑器会吞掉单个换行**，
   按钮复制时自动把每行加固成「空行分隔」，粘贴即正常分行；手动选中复制会踩同一个坑。
   第一行即标题（≤20 字），补齐话题
7. 选一首 BGM（抖音图文支持配乐，能显著提升完播）
8. 确认封面（默认首图，可换）
9. 发布，或用定时发布

全程不接入任何第三方自动化工具，账号无风控风险。

> **若用户明确要求做发布自动化**：优先给 `references/why-no-autopublish.md`
> 末节的「本机半自动助手」方案——自动上传全部图 + 自动填文案话题，**停在发布页由人工点发布**。
> 它零新增依赖（playwright-core 与本机夸克均已就绪），且**直接用夸克本体跑、不搬 Cookie**、风险最低，
> 也是官方入口，不触碰平台协议。**不要默认推荐全自动直发方案。**

**配乐（BGM）**：图文也能配 BGM（发布页有「选择音乐」入口，本机实测确认）。
选用的完整规则、内容基调→曲风映射表、站内检索关键词、版权的三条线，
见 `references/bgm.md`。**用户偏好柔和**，默认给柔和方向；核心判断是
「图文没有完播率，音乐只做情绪底色，越没存在感越对」。

**发布时间参考**（社区经验，非官方）：工作日 07:30–08:30、18:00–19:30；
避开午间 12:00–13:30 与 22:00 之后。

## 常见坑

- **改 cards.html 时，多处修改必须串行提交，不要并行发多个 Edit。**
  实测（2026-09-28）：对同一文件并行发 3 个 Edit，**只有 1 处生效，另 2 处被静默覆盖**，
  而每个 Edit 都返回「成功」。改完必须用 Grep 回头确认每一处都落盘。
- **别把爆料写进首行。** 首行即标题，是最容易被读者截图打脸的地方。
- **第 2 张不要写成第 1 张的补充说明。** 这是抖音图文最常见的死法。
- **别漏掉原文里对自己不利的那句话。** 平衡信息必须保留，删掉它会让笔记变成不实宣传。
- **评测 / 排名类内容必须写清「版本 + 时点」。** 榜单口径会变，只写「得 X 分」不写版本，
  一天后就可能被打脸。
- **单图信息别塞太满。** 容量按上文「单页信息量」表来（**4 条 `item` 或 5 条 `point`**）。
  **此处早期版本写的「2–3 条为宜、超过 4 条就崩」是经验建议值、已过期**，与容量表自相矛盾，
  2026-09-29 实测 4 条 `item`、6 条 `point` 均正常（后者填充约 90%，已接近上限）。
  超过 6 条才需要拆页，拆页比压缩好。
- **自主声明：固定选「内容由AI生成」，脚本代选**（2026-10-05 用户明确：
  「后续的自主声明，你就改成『内容由AI生成』这一个吧，把所有都改了」）。
  **执行口径：配置里 `自主声明` 字段写「内容由AI生成」，`pub_fill.cjs` / `pub_fill_multi.cjs`
  会点开控件、选中、确定；脚本默认值也已同步改成它。**
  ⚠️ 历史沿革（别来回改）：早期写「【必做】勾选 AIGC」→ 2026-09-29 改为「不代操作、保持默认」
  → **2026-10-05 用户改为固定选「内容由AI生成」，以本条为准**。
- **话题：总数不超过 5 个，且不要用泛流量大词堆。** 50 万播放的精准话题比 5 亿播放的泛话题有用得多。
  （上限 5 个是用户 2026-09-30 的硬规则，与上文「首行 / 正文」字数限制同节，别再按 7 个出稿。）
- **验证汇总 HTML 时，图片是懒加载的，必须先滚动再统计。**
  实测（2026-09-28）：直接读 DOM 会得到 `imgs_loaded 3/9`，看着像加载失败，
  实际是 `loading="lazy"` 的视口外图片还没触发。正确做法：先逐段 `window.scrollTo`
  滚完一整轮再统计，或直接以 `FAILED_REQ 0` 为通过标准。
- **Playwright 的 `page.screenshot({clip})` 不能超出页面可截区域**，
  否则报 `Clipped area is either empty or outside the resulting image` 并中断脚本。
  分段截图要用「滚动到位置 + 视口截图」，不要用 clip 硬切。
