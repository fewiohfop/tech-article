# 为什么发布环节不做自动化（抖音）

调研时间：2026-09-28。结论：**前七环节全自动，第八环节交回人工。**

## 官方接口的真实开放度

**抖音确实有内容发布接口。** 抖音开放平台设有「发布内容至抖音」能力，
含 `创建图文作品`、`上传图片`、`创建视频作品`、`上传视频`（含分片上传）等接口。
图文场景是**真支持**的。

但门槛写在申请条件里，是三重叠加：

| 层级 | 要求 |
|---|---|
| 主体资质 | **企业开发者主体**（个人开发者权限受限，无法开通），需营业执照、法人身份证、对公账户 |
| 认证费用 | 企业认证 **600 元/年** |
| 应用资质 | 自有**已备案的 HTTPS 域名**（不支持 IP、未备案域名），创建网站应用（Web/H5） |
| 权限审核 | 逐项申请（`发布内容至抖音` + H5 分享场景 + `获取 openTicket`），每项都要写场景说明、页面截图、交互演示，**审核约 7 个工作日** |
| 持续义务 | 平台保留**不定期回查**（会要应用地址、测试账号），滥用可随时收回并追责 |

**最关键的一点：即便如此，它也不是静默直发。**
H5 场景的做法是生成抖音扫码 / Schema 链接，**拉起抖音 App 把内容送进发布页，由用户在 App 内手动确认**。
另外官方明确的限制还包括：营销类应用不开放，禁止用「抖音官方」等字样外宣，
且仅限 C 端创作分享场景。

**结论：对个人创作者来说，「无人值守发布」在官方路径下走不通**——
不是技术问题，是主体资质和审核门槛的问题。

## 非官方自动化的真实代价

社区有第一手复盘，模式高度一致——工具能跑通，账号被封：

- 有人用 `social-auto-upload` 做「采集 → AI 生成 → 渲染 → 自动定时发布」全链路，
  首次真实发布后 3–4 天，**账号被限制 7 天**。
- 平台处罚通知原文：**「账号多次利用 AI 托管进行发文 / 互动，我们将限制您的账号功能」**。
- 另一用户用全自动托管方案，完整走完 **轻微限流 → 重度降权 → 永久封禁**。
  其复盘原话：**不存在「调低速度就能规避风控」**，HTTP 直连与浏览器自动化两类方案都无法长期规避检测。

> 注意：上述复盘多来自小红书场景，但处罚逻辑（AI 托管发文判定）在两个平台的社区反馈中一致。
> 抖音侧的同类案例本机未能取得第一手链接，**按推测处理，未验证**。

## 所以这套流程的边界

- ⓪ 选题 → ① 输入 → ② 提纯 → ③ 核验 → ④ 重组 → ⑤ 改写 → ⑥ 出图 → ⑦ 汇总：
  **100% 自动、不接触登录态、零风控风险**
- 上传与点发布：**人工**，走抖音 App 的图文入口

拿到的效率提升约 90%，代价是最后点一下。用账号去赌剩下那 10%，不划算。

## 如果将来仍要做全自动

必须同时满足，缺一不可：

1. 先拿**小号**验证，绝不用主号
2. 接管真实浏览器（不用无头模式）
3. 发布节奏随机化
4. 检测到风控信号立即熔断
5. 标题与话题差异化，避免模板化特征
6. 单号每天不超过 1 篇

即便如此，也无法保证长期可用。且抖音官方接口路径仍需要企业主体，个人拿不到。

# 附：现成自动化方案盘点（2026-09-28 补充调研）

用户明确要求「走现成项目改造，避免自己踩坑」。以下是真实存在的方案，按风险从低到高：

| 方案 | 形态 | 抖音图文能力 | 账号风险 | 落地成本 |
|---|---|---|---|---|
| **本机半自动助手** | 自建：Node `playwright-core` + 本机真实 Chrome | 自动上传全部图 + 自动填文案话题，**停在发布页等人工点** | **最低** | **零新增依赖**（playwright-core 与 Chrome 本机已有） |
| **Douyin Publisher** | 开源 skill（Playwright，Python） | ✅ 上传 + 填充，**只保存到草稿箱，不直接发布** | 低 | 需装 `playwright`（Python）+ 浏览器 |
| **douyin-creator** | 开源 skill / CLI（mf-yang、wukangcheng2944 两个实现） | 🚧 图文发布标注为「待实现」，当前以登录/会话管理为主 | 中 | 需 `npm i -g`，会自下 Chromium |
| **social-auto-upload** | 开源 CLI（11K★，主力项目） | ✅ **完整**：登录 + 图文上传 + 定时发布，CLI 与 Skill 均已接入 | **高**（全自动直发） | 需 Python venv + `playwright` + `patchright install chromium` |

## 关键判断：「存草稿」是风险最低的中间态

全自动直发（social-auto-upload 路线的默认用法）要拿账号赌；纯手工又浪费掉全部重复劳动。
**把自动化做到「图传完、字填好、存进草稿箱或停在发布页」，最后一下由人点**，是收益/风险的拐点：

- 省掉的是最耗时的部分（选图、上传、排版文案、配话题）
- 保住的是账号（人工确认这一步让「AI 托管发文」的判定不成立）
- 抖音创作者中心本身就是官方入口，不存在第三方协议冲突

## 本机实践路径（零新增依赖）

```powershell
$env:NODE_PATH = '<含 playwright-core 的 node_modules>'
& '<node.exe 路径>' '<脚本路径>.cjs'
```

要点：

1. 用 `chromium.launchPersistentContext(profileDir, { executablePath: 本机 Chrome, headless: false })`
   —— 登录态存在独立 profile 目录（`~/.douyin-pub/profile`），**首次扫码后长期复用**
2. 加 `--disable-blink-features=AutomationControlled` 并去掉 `--enable-automation`
3. 图文发布入口：`creator.douyin.com/creator-micro/content/upload`
4. 未登录时页面会停在扫码登录页，二维码可直接用手机 App 扫
5. **不要把 profile 目录设成日常 Chrome 的 `User Data`** —— 会与正在运行的 Chrome 抢锁

> 实测（2026-09-28）：`creator.douyin.com` 与其 `/creator-micro/*` 子路径本机均可达（HTTP 200），
> 未登录时渲染为扫码/验证码/密码登录页。**发布自动化在技术上没有障碍，取舍只在账号风险。**
