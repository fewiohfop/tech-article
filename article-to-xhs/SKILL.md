# article-to-xhs · 文章转小红书图文

## 这个 skill 解决什么

输入一篇 AI / 科技类文章（也兼容其他领域），输出一套可直接上传的小红书图文：
封面 + 内页的 3:4 卡片 PNG、标题候选、分点正文、标签，以及一个汇总单文件 HTML。

**不包含自动发布。** 发布走小红书官方创作服务平台的定时发布，由用户点最后一下。
原因是全自动发布会让账号承担封禁风险，详见 `references/why-no-autopublish.md`。

**抖音是另一套流程**（文案长度、图片比例、话题玩法都不同），见 `article-to-douyin`，
不要在本次流程里顺带产出抖音内容，两套混做容易互相污染。

---

## 执行流程（九个环节）

```
⓪ 选题发现 → ① 输入 → ② 提纯 → ③ 事实核验 → ④ 结构重组 → ⑤ 改写 → ⑥ 出图 → ⑦ 汇总HTML → ⑧ 刷新总索引
   全自动 ──────────────────────────────────────────────┘                      ↓
                                                                    人工：官方入口定时发布
```

### ⓪ 选题发现（用户说「今天发什么」「帮我找点素材」时执行）

#### 🚧 与「常规热榜」严格分离（用户 2026-09-29 明确要求）

**本环节产出的是「AI 科技选题池」，不是「今日热榜」。两者必须分开，不得混在一份文件里。**

| 属于本池（用） | 不属于本池（不用） |
|---|---|
| 今日热榜的**科技 / AI 分类节点**（媒体源，带原始链接与热度） | **抖音热搜 / 微博热搜 / 百度热搜 / B站热搜 / 快手热搜** |
| **X 聚合站**（境外 AI 前沿，二手转载需回一手核） | 抖音**总榜**（属 `article-to-douyin` 的独占源，本 skill 不用） |
| **GitHub Trending**（工具向补充） | 影视票房、音乐榜、App Store 榜、报纸版面 |
| Hacker News / Reddit（需 VPN，技术社区） | 任何「社会话题榜」「吃瓜榜」 |

理由（用户原话的意思）：常规热榜是「今天大家在聊什么」，跟账号的 AI / 科技定位错配，
混进来只会把选题池稀释掉。**要看常规热榜就单独出一份，别合并。**

#### 🚧 选题不看用户背景（用户 2026-10-01 明确要求）

**做选题发现时，不要把用户的个人背景、职业经历、以往内容方向当作筛选或加权因素。**

- ❌ 不做「这个跟他以前的经历有关，优先给他」
- ❌ 不做「这不在他的舒适区 / 他没做过这个方向，略过」
- ✅ 只按内容本身判：**此刻热度 + 可做度 + 与账号 AI/科技定位是否匹配**

> 与「发布前查重」不冲突：查 `C:\小红书\` / `C:\抖音\` 已有目录、同一事件做过就 pass，
> 是用户单独提出的硬规则，**继续执行**。本条取消的是**选题阶段的个人化加权**，不是成稿前的去重。

**上面任选一句即可，不需要复述下面的规范。**

> ⚠️ 下面这份是**执行规范，写给 AI 看的，用户无需念出来**：

```
跑一遍选题发现：
1) 只用 AI / 科技内容源——今日热榜的科技与 AI 节点 + X 聚合站 + GitHub Trending；
2) 常规社会热榜（微博/百度/B站/快手/抖音热搜）不要混进来；
3) 同一条被多源命中的合并成一条，标出命中源数量；
4) 每条给出：标题 / 命中源 / 热度或数据证据 / 2–3 个可做角度 / 风险提示；
5) 单源条目单独标「单源待核」；
6) 采不到的源如实写在末尾并写明原因，不要跳过、不要用推测补；
7) 产出单文件 HTML，存到 C:\小红书\选题\今日AI科技选题池_<日期>.html。
```

**X / Reddit / 境外站点的可达性已实测**（含开 VPN 后的复测），别重复踩坑，动手前先看 `references/sources.md`。

全部带 X 原帖引用。**注意这批站以「AI 模型」新闻为主，机器人 / 芯片类命中率低**，
那类需求改用通用检索或国内媒体。

> ⚠️ 聚合站仍是**二手转载**。进 ③ 事实核验时，具体数字必须回到一手源
> （官方博客 / 原始论文 / 原帖）复核，**不可直接当 L1 使用**。

### ① 输入：拿到干净正文

按顺序尝试，成功即停：

1. **WebFetch 直接抓**（首选，36氪、机器之心、量子位、知乎、掘金、tophub 等大多数站点直接可读）
2. **本机 Playwright 抓取**（Chromium 已装好，见下文环境路径），用于第 1 步失败的场景
3. **用户粘贴的原文**：直接使用，零风险

**Jina Reader 已不可当免费降级用。** 2026-09-28 实测，`https://r.jina.ai/{URL}` 对
**任意** URL（含 `example.com`）一律返回 **403**，需自行申请 API Key 才能用。
（本 skill 早期版本写「免费无 Key、约 200 次/天」，该说法已过期，勿再沿用。）

**已知硬骨头：微信公众号文章。** 普通抓取会被中断，直接向用户要正文，
不要反复重试浪费轮次。

抓取时要求：保留小标题、全部数字、公司名 / 产品名 / 人名、引用原话。**不要让它总结。**

### ② 提纯：抽出事实内核

从正文里抽出结构化的事实清单：数字、版本号、机构名、时间点、结论、争议点。
逐条与原文对齐，**不得漂移、不得外推、不得补全原文没说的因果关系**。

### ③ 事实核验（必做，不可跳过）

**这一步是本 skill 与普通「一键生成」工具的核心差别。**

用 WebSearch 对事实内核里的关键点做交叉检索，按三级标注：

| 级别 | 判定标准 | 处理方式 |
|---|---|---|
| **L1 共识** | ≥3 个独立来源一致，或官方（官网 / 财报 / 官方博客 / 官方公告）直接发布 | 正文正常写，**不必逐条标来源** |
| **L2 据报道** | 1–2 个可信媒体来源（主流科技媒体、正规财经媒体） | 正文用「据报道」「XX 称」，**一句带过** |
| **L3 爆料 / 传闻** | 社交媒体、社区流传、单一匿名源、泄露截图、厂商自述 | **必须在图文里显式标注「未经官方确认」**，且不能写进标题当结论 |

同时必须做的三件事：

- **找反方。** 至少检索一次「质疑 / 反驳 / 不能证伪 / 未经验证」这一侧。原文说得越绝对，越要找平衡信息。
  例：原文称「碾压竞品」时，要主动去找该结果是否来自统一受控评测。多半不是。
- **修正原文的绝对化表述。** 原文常见的「碾压」「彻底告别」「壮士断腕」这类词，
  在核验后如果缺乏支撑，改写时要降级为「在这组测试中超过」。
- **写清分歧。** 多个来源互相矛盾时，把两种说法**并列写出**，不要挑一个当定论，也不要取平均。

核验结果要落成一张表（信息点 / 来源数 / 级别 / 备注），放进 ⑦ 的汇总 HTML。

**⚠️ 选题池里的判断，出成品前必须逐条回搜验证（2026-09-30 踩坑）**

从 ⓪ 选题发现产出的池子里挑条目时，池子里写的「数字」和「落差/冲突」是**当时的快速判断**，
不是已核验结论。进 ③ 时必须把它们当**待验证的假设**，而不是可以直接抄的事实。

实测踩到的两类坑：

1. **数字被记错**：池子写「缓存输入价从 $1 降到 $0.10」，核验后实为 **$0.20 → $0.10**
   （$1 是另一个型号的缓存价）。这类错误来自把同批新闻里两个型号的数字串了行。
2. **「落差」是编出来的**：池子写「国内标题写成『因新模型太强叫停发布』」，
   回搜后**找不到任何一篇国内标题作此表述**（实际是「紧急叫停」「重大突发」这类戏剧化框架）。
   整条内容原本就靠这个落差立住，如果不验证直接写，等于替读者编了一个因果。

处理原则：
- 池子里的每个**具体数字**，进 ③ 都要回到一手源核一遍；
- 池子里的每个**口径分歧 / 反差**，必须能指名到具体来源的具体表述。
  **验证不通过就换角度，不要为了让内容好看而保留**——这是「事实与推测分栏」的底线。
- 换角度后的写法示例：把「国内标题说太强」换成可验证的反差
  ——「跑分 98%/99.9%/100%，却因可靠性不达标被按下」。同样有张力，但每句都能核。

判断标准可参考 `references/fact-check.md`。

### ④ 结构重组（**先重组，再改口吻**）

**不要顺着原文的段落顺序改写**——那是洗稿的特征。按三步走：

1. **拆**：把 ② 的事实内核拆成彼此独立的信息点，脱离原文叙事顺序
2. **重排**：选一个阅读骨架，**骨架不得沿用原文的**：
   - 结论先行（评测、数据类）→ 对比反转（争议、辟谣类）→ 时间线（事件演进）
   - 问答（高密度干货）→ 数字拆解（单点数据冲击）
3. **重述**：换句式而不只是换词；连接词改口语方向；段落长短打散

**重制的底气来自「信息增量」**——③ 核验查出来的版本时点、反方声音、口径分歧、
原文里对自己不利的平衡信息，都是原文没有的内容，这才是与洗稿的分水岭。
若笔记里找不到 2 条原文没有的信息，说明 ③ 没做透，回去补查。

发布前的自检四问（结构是否一眼不同 / 有无连续 15 字雷同 / 有无 2 条增量 / 有无直接搬原文小标题）
见 `references/rewrite-structure.md`。

| 小程序「**云上**」模式 | ❌ **不加载本地 skill** | ❌ 只见上传件 | ❌（推断：沙箱未预装 Chromium，未实测） | ❌ |

**结论：手机端要用整套流程，就走「电脑」模式（远程连本机），不要走「云上」模式。**
此时任务实际跑在**电脑**上，skill / 脚本 / 模板全部原样可用，手机只当遥控器和看板；
代价是**电脑需开机并联网**。

### 只有云上模式时（电脑不在线），可做的降级

- ✅ **选题发现**：联网检索 + 筛选可用，`⓪` 整节照跑。
- ✅ **核验 / 重组 / 改写**：`③④⑤` 是纯推理环节，完整可用。
- ✅ **文案自查**：云上没有本机脚本，**改由模型按规则自己数**——
  标题 ≤20 字、正文 ≤1000 字、**话题 ≤5 个**，中文按字符数计（含全角标点），超一个字都发不出去。
- ⚠️ **违禁词自查**：云上读不到 `banned_words.json`，改为**按类别清单逐条比对**：
  绝对化用语（最好 / 第一 / 最优 / 顶级）、医疗功效、金融诱导、迷信、站外导流、
  敏感营销词。**高危词必须清零再往下走。**
- ❌ **出图**：云上渲染不出 PNG。**卡片清单可以出**（每页：页号 / 小标题 / 要点数组 / 参数行），
  PNG 回电脑补渲染。

```bash
python scripts/env_check.py           # 只读；列出各组件实际位置与缺失项

```

下表是 Windows 上的**典型位置**（本机 2026-10-05 核对）。换设备 / 上云端后**不要照抄**，
以自检输出为准 —— 用户名、Node 版本号都会变。

| 组件 | 典型位置 | 用途 |
|---|---|---|
| Node | `C:\Users\<用户名>\.workbuddy\binaries\node\versions\<版本>\node.exe` | 跑 `render.cjs` |
| playwright-core | `C:\Users\<用户名>\.workbuddy\binaries\node\workspace\node_modules`（用 `NODE_PATH` 引入） | 渲染依赖 |
| Chromium | 脚本自动扫描 Windows / Linux / macOS 常见位置 | 出图内核 |
| Python + Pillow | `C:\Users\<用户名>\.workbuddy\binaries\python\envs\default\Scripts\python.exe` | 密度 / 尺寸 / 文案校验 |

**依赖构成（实测）**：三支相关 skill（本 skill、`article-to-douyin`、`github-trending-official`）
的 Python 脚本里，**唯一的第三方依赖是 Pillow** —— 只被 `article-to-douyin/scripts/check_density.py`
用来读 PNG 算底部留白，其余全部为标准库；Node 侧只需要 `playwright-core` + 一个 Chromium。

**跨设备覆盖方式**（都不需要改代码、也不需要改本文件）：

| 要覆盖什么 | 环境变量 | 说明 |
|---|---|---|
| Node 可执行文件 | `NODE_BIN` | 仅在 node 不在 PATH 时用；`env_check.py` 会读它 |
| playwright-core 位置 | `NODE_PATH` | 指向含 `playwright-core` 的 `node_modules` |
| Chromium | `PW_CHROMIUM` / `PLAYWRIGHT_BROWSERS_PATH` | 前者指可执行文件，后者指浏览器根目录 |

**不要 `pip install` 或 `npm install -g`**，所有依赖已在隔离目录内。

换到全新环境（例如云端 Linux 沙箱）时，按自检输出的缺失项补装即可：
`npx playwright install chromium`；中文字体缺了中文会渲染成方块，Debian 系装 `fonts-noto-cjk`。

## 常见坑

- **改 cards.html 时，多处修改必须串行提交，不要并行发多个 Edit。**
  实测（2026-09-28）：对同一文件并行发 3 个 Edit，**只有 1 处生效，另 2 处被静默覆盖**，
  而每个 Edit 都返回「成功」。极易漏改且不报错。改完必须用 Grep 回头确认每一处都落盘。
- **别把爆料写进标题。** 标题是最容易被读者截图打脸的地方
- **别漏掉原文里对自己不利的那句话。** 例：原文承认「某些任务仍会输给竞品」，这类平衡信息必须保留，
  删掉它会让笔记变成不实宣传
- **评测/排名类内容，必须写清「版本 + 时点」。** 榜单口径会变——本条实测中，同一模型在
  两周内因评测机构三度更新方法（v4.1.1 → v4.2 → v4.3），排名从第 5 变成并列第 1。
  只写「得 X 分」而不写版本，一天后就可能被打脸。
- **单图信息别塞太满。** 内页超过 6 条视觉就开始崩，拆页比压缩好
- **图片上限 18 张**（用户 2026-09-29 明确给出；本 SKILL 此前的「4–9 张」是**经验建议值**、
  不是平台上限，勿再混淆）。**清单型内容**（榜单、合集、逐项介绍）可放宽到 18 张；
  **叙事型图文**仍建议 4–9 张——少于 4 张撑不起内容，多于 9 张完读率会掉
