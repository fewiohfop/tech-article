# github-trending-official · GitHub 选题 → 图文

## 这个 skill 解决什么

把 GitHub 生态里的「热度」和「好用」转成可直接上传的小红书 / 抖音图文。
**两个选题方向，两套内容结构**，共用同一个数据源层。

| | 方向 A · 榜单型 | 方向 B · 推荐型 |
|---|---|---|
| 选题 | GitHub 日榜 / 周榜 | 好用的项目 / 工具 |
| **一篇是几篇** | **一个榜 = 一篇图文。日榜、周榜各自独立成篇，绝不混排**（2026-09-29 用户明确） | **一个项目 = 一篇图文**（2026-09-29 用户明确） |
| **取几条** | **只取前 5 条或前 10 条**（2026-09-29 用户明确），不必把整榜搬进去 | 一篇一个，不横评 |
| **内页怎么排** | **第 2 页起「一页一个项目」**（2026-09-29 用户明确）。每个项目一页，页内固定四件套：**能给什么 · 用在哪 · 有啥实例 · 上手门槛** | 同上，一页一项目本来就是它的形态 |
| **封面日期** | **封面不写日期**（2026-09-29 用户明确，理由：成品可能提前做，写死日期会过期） | **同左**。日期只放在正文与页脚 |
| **必须有实例图** | 榜单页本身就是实例（页面上附增量数字） | **必须放真图，不许光写文字**（2026-09-29 用户明确）。封面与专属实例页各一张：优先**自己实跑生成**，其次用官方实测样图并标注来源 |
| **怎么让读者拿到它** | 榜单页附仓库名，读者自己搜 | **小红书：全篇只给一个项目名称，不设「怎么安装」页；抖音：保留「上手门槛」页，但仍不写技能名、不给外链**（2026-09-29 末次修订，按平台分开）。详见下方「方向 B：怎么让读者真的拿到它」 |
| **文案字数** | **标题 ≤20 字、正文 ≤1000 字，硬规则**（2026-09-29 用户在小红书后台实测，两套成品都因超字发不出去）。正文目标 600–900 字留余量 | **与左侧完全相同**：首行即标题 ≤20 字、正文 ≤1000 字，**同为硬规则**（2026-09-29 用户最终更正：「两边都是标题 20 字，正文 1000 字」）。⚠️ 中途一度放宽为「抖音 35 字 / 底线 2000 字」，**该口径已作废** |
| **正文必须带 emoji 分段** | 必须。**开头 1–2 段纯文字交代事实 → 3–5 个「🐰 小标题」段落 → 结尾号召 + 提问**，emoji 只在段首，一篇 4–6 个（2026-09-29 用户以「太空兔」那篇为样板明确） | **同左**。这是小红书读者的阅读习惯，**不是可选项**；光排版好看、正文没 emoji，用户会判为「不像小红书」 |
| 判断依据 | **star 增量**（客观排序） | 多渠道交叉判断（见 `references/pick-sources.md`） |
| 首页 | 直接上**该榜的总榜单** | **钩子 / 最强卖点** |
| 后续页 | **一页一个项目**，每页四件套（能给什么 / 用在哪 / 有啥实例 / 上手门槛） | 项目背景 → 能做什么 → 实例认证 |
| 结构细节 | `references/content-structure.md` §A | `references/content-structure.md` §B |

> **方向 A 一次出两篇**（日榜一篇、周榜一篇），但**两篇分开做、分开上传**，
> 不要为省事把两个榜塞进同一条图文。素材可以同一批抓取，成品必须两份。

**发布不含在本 skill 内**，交回 `article-to-social` 的发布环节。

## ⚠️ 口径：什么才算「热」

**判断口径是否正确的唯一标准：有没有「增量」字段。**

| 来源 | 给的是 | 能不能当热榜 |
|---|---|---|
| `github.com/trending` 官方页 | **stars today / this week** 增量 | ✅ 唯一正确口径 |
| GitHub Search API `sort=stars` | 总 star 数 | ❌ **不是热榜** |
| GitHub Explore | 官方运营挑选 | ✅ 但属「推荐」不是「热度」 |

已被停用的 `github-trending-cn`（市场版）就是踩了这个坑：
它用 `pushed:>=日期` + 按**总** star 排序，2026-09-29 实测返回的前几名是
public-apis（48.4 万★）、freeCodeCamp（45.6 万★）、react、linux kernel——
**历史总星榜**。一个 48 万星的仓库今天涨 3 颗星也照样排第一。
（该 skill 已移到 `~/.workbuddy/_disabled_skills/`，需要可随时移回。）

### 星标数与「最后更新」：一律取 GitHub API，不用第三方页面

2026-09-29 实测踩到的错误：从 HelloGitHub 页面抄下来的星标数与 GitHub 实际
**差一个数量级**——

| 项目 | HelloGitHub 页面 | GitHub API 实测 |
|---|---|---|
| yang0/handraw-style | 228 | **3,588** |
| ChenLiu-1996/figures4papers | 173 | **7,703** |
| TencentCloud/TencentDB-Agent-Memory | 167 | **27,423** |

**未能确认 HelloGitHub 那一栏到底是什么口径**（是星标？收藏数？站内热度？），
所以不猜、直接换源。凡涉及星标、fork、open issues、许可证、建仓时间、
**最后更新时间**，一律打 `https://api.github.com/repos/<owner>/<repo>`。

- **「最后更新」= `pushed_at`**（最后一次推送代码），不是 `updated_at`
  （后者连收 star、改 issue 都会变，会被误读成「还在开发」）。
- 换算成北京时间日期再展示；**不要显示 UTC 日期**，会差一天。
- 星标是实时值，**必须同时给抓取时点**，否则第二天就变成假数据。

### 周榜的采集时间：官方是「滚动 7 天」，不是自然周（2026-09-29 用户提问后查证）

用户明确要**固定一个采集时间**，并问「官方本身有没有周榜、按哪个时间走」。
查证结论如下，**事实与推断分开写**：

| | 内容 |
|---|---|
| **事实：官方有周榜** | `https://github.com/trending?since=weekly` 就是官方周榜页，日 / 周 / 月三档都在 |
| **推断：口径是滚动 7 天窗口** | 3 处互相独立的第三方描述一致指向「rolling 7-day window，不是自然周一到周日」。**GitHub 未在官方文档里定义 trending 页口径**，也没开放 trending API，故本机无法取得官方书面说明 |
| **事实：没有官方 API** | trending 数据只能抓页面 HTML；页面展示有缓存延迟 |

**执行规则（固定采集时间）**：

1. **每期固定同一时刻抓一次**，推荐**每周一 09:00（GMT+8）**。
   因为官方是滚动 7 天，固定时刻 = 每期覆盖「抓取时刻往前推 7×24 小时」，**两期之间不重不漏**。
2. **成品里必须写明具体时间与口径**，例如「滚动 7 天窗口 · 本次抓取 2026-09-29 09:1x（GMT+8）」。
   用户明确要求：「把具体时间告诉我是哪个时间」。
3. 若用户想按**自然周一→周日**走，那是**另一种口径**，要在图里改口径说明；
   此时建议改为**每周一早上抓「上周一至周日」**，并注明「本榜按自然周统计，与官方滚动 7 天窗口有差异」。
4. 时区固定写 **GMT+8**，不要写 UTC。

## 让 AI 更快读懂一个 GitHub 仓库（2026-09-29 实测）

写方向 B 的「能带来什么」时，光看仓库描述往往不够，需要读 README 甚至架构。
除了直接抓 `raw.githubusercontent.com`，还有几个**把 `github.com` 换掉**的入口：

| 把 `github.com` 换成 | 得到什么 | 实测结果 |
|---|---|---|
| **`deepwiki.com`** | **AI 生成的仓库 wiki**：架构分层、模块职责、请求流程，且引用**带行号**的源码链接 | ✅ **已验证可用**。WebFetch 直接读到完整架构文档；写「项目背景 / 能做什么」时信息密度最高 |
| `gitingest.com` | 整仓转成喂 LLM 的纯文本摘要（含文件树、体积、token 数） | ⚠️ **部分**。官方说明是「把任意 GitHub URL 里的 `hub` 换成 `ingest`」；但页面是 SPA，WebFetch 抓不到正文 |
| `uithub.com` | 仓库转纯文本 | ❌ **需登录**（返回「Content hidden. Please sign in to continue.」） |
| `gitmcp.io` | 给仓库起一个 MCP 端点 | ⬜ 未实测 |
| `gitdiagram.com` | 把仓库画成架构图 | ⬜ 未实测 |

另外还有一个 **GitHub 自带的「后缀」**（这才是真正的加后缀）：

```text
https://github.com/<owner>/<repo>/blob/main/README.md?plain=1
```

加 `?plain=1` 显示**纯 markdown 原文**而不是渲染后的 HTML，AI 抓取时更干净。

> 用法建议：README（`raw.githubusercontent.com`）看**功能与用法**，
> DeepWiki 看**架构与模块**。两者互补，别只用一个。

**方向 B 的选取标准**（不是有热度就算）：
1. **有明确使用场景** —— 能一句话说清「谁在什么情况下会用它」
2. **上手成本可描述** —— 能写清装什么、要不要账号、要不要花钱
3. **有实证** —— Demo / 截图 / 真实数据 / 用户反馈至少占一样
4. **还活着** —— 近期有提交或发版；僵尸项目不推
   （**判据就是 `pushed_at`**。2026-09-29 实测：`rakyll/hey` 停更 8 个多月、
   `PLFM_RADAR` 停更 3 个多月、`srt-whiteboard-animation` 停更 2 个月——
   这类项目可以写，但**文案必须写「经典工具」而不是「活跃项目」**）
5. 与已发过的内容不重复

判不准的项目送 `github-check`（市场 skill，判断是否刷 star / 可否安全采用）。

## 多端执行：选题在手机 / 云上怎么做（2026-09-29 补）

选题这一步的**数据可靠性**取决于跑在哪：

| 执行环境 | 本地 skill | 抓取方式 | 口径可靠性 |
|---|---|---|---|
| 桌面端 / 微信直连 / 小程序「**电脑**」模式 | ✅ 加载 | `github_trending_official.py` 直抓官方 trending 页 + GitHub API | ✅ 官方口径（star 增量、`pushed_at` 都是真值） |
| 小程序「**云上**」模式 | ❌ **不加载本地 skill** | 只能用通用联网检索（搜索 + 读页面） | ⚠️ 降级——star 增量、最后更新时间**可能取不到或不准** |

**结论：要「官方口径」的数字，选题就必须跑在电脑上**（桌面端，或小程序切「电脑」模式远程连本机）。
云上模式能出**选题方向**，但**数字必须标为未核实**，不得当事实写。

### 云上模式下的选题降级规则（电脑不在线时）

1. **可以做的**：从公开检索里找出「项目名 + 一句话价值 + 大致热度」，产出候选清单。
2. **不能做的**：**不得输出精确 star 增量、不得声称「本周 +N 星」**——
   这些必须来自官方 trending 页或 GitHub API，云上取不到就留空。
3. **凡未经官方口径核实的数字，一律写 `[待核实]`**，回电脑后补跑脚本填回。
4. **交付形态不变**：选题池 HTML 的方向 A / 方向 B 两节照旧，只是数字位留空。
5. 后面「生成图文」那段见 `article-to-social` 的「多端执行」一节。

## 脚本用法（方向 A）

```bash
# 变量取法见文末「环境」章节；路径随设备变化，**不要写死**
PY=<Python 解释器实际路径>
S=<本 skill 目录>/scripts/github_trending_official.py

# 日榜 / 周榜 / 月榜
"$PY" "$S" --period daily  --limit 20
"$PY" "$S" --period weekly --limit 20
"$PY" "$S" --period weekly --language python --limit 10

# JSON（给后续步骤消费，含 period_stars 增量字段）
"$PY" "$S" --period daily --json --out out.json

# 【抓取资料，不是成品】日榜 + 周榜合一的单文件 HTML，供选题与查数用
"$PY" "$S" --html --limit 25 --out "<成品根目录>/选题/GitHub热榜_YYYYMMDD.html"
```

| 参数 | 简写 | 默认 | 说明 |
|---|---|---|---|
| `--period` | `-p` | `daily` | `daily` / `weekly` / `monthly` |
| `--limit` | `-n` | `15` | 上限；**实际条目数由官方页决定，脚本不补位** |
| `--language` | `-l` | 空 | `python` / `go` / `rust` 等 |
| `--json` | — | 否 | JSON 输出 |
| `--html` | — | 否 | 日榜+周榜合一 HTML |
| `--out` | — | 空 | 写 UTF-8 文件。**建议总是带上** |

输出字段：`rank / name / url / description / language / stars / forks /
period_stars / is_tool`。

`is_tool` 是按关键词（skill / agent / cli / mcp / template / plugin / harness /
memory / tool）做的**启发式**标记，**不是官方分类，成品里不得当事实陈述**。
它只用于快速筛出方向 B 的候选。

仓库字段（含「最后更新」）用另一个脚本抓，一次取一批：

```powershell
# 见本 skill 的 _build 参考实现；核心就是逐个打 api.github.com/repos/<owner>/<repo>
# 取 pushed_at / stargazers_count / forks_count / open_issues_count / license / topics
# 顺序请求 + 0.6s 间隔，30 个仓库约 40 秒；写入 UTF-8 JSON 再消费
```

## 选题池的交付形态（用户 2026-09-29 明确要求）

选题阶段**本身就是一次交付**，不能只在对话里列一串项目名。硬要求：

1. **每条都要带介绍信息** —— 项目名 / 语言 / 总星 / 周期增量 / 说明。
   **说明要写得厚**：用官方仓库 description + topics + README 事实扩写成 2–3 句，
   不要只留一句干巴巴的定位。用户 2026-09-29 明确要求「介绍再尽量详细一下」。
2. **每条都要带「最后更新时间」**（用户 2026-09-29 明确要求）。
   取 API `pushed_at`，换算北京时间日期，停更的加醒目标记。
   **非仓库条目**（Marketplace 应用、Collections 合集、Product Hunt 产品）
   **不是仓库、该字段不适用**——留空并写明原因，不要填「—」了事，更不要猜。
3. **每条都要带原文跳转链接** —— 写 `<a href="https://github.com/owner/repo">`，

   第三方源（HelloGitHub 等）的收录页可另附，但项目主链接必须是 GitHub 原文地址。
4. **成品是单文件 HTML**，落到 `C:\小红书\选题\` 与 `C:\抖音\选题\` 各一份。
   命名：`选题池_<主题>_<YYYYMMDD>.html`。
5. **必须标注的元信息**：抓取时点、数据源 URL、口径说明（增量 ≠ 总星）、
   **字段定义**（如「最后更新 = pushed_at」）、**缺失字段**（如官方描述为空）、
   以及**待核实项**（长期未更新 / 星标数来源不同）。
6. **重复条目要标出** —— 同一项目同时出现在周榜与 HelloGitHub 这类情况下，
   打上「与周榜第 N 名重复」标记，避免用户重复选择。
7. 结尾给**挑选建议**：哪些值得先做、理由是什么、哪些需要先核实。
   用户会自己选，但也要能接受「你帮我判断」。
8. **修订要写进文档里，不要静默改。** 若上一版有错（如星标数取错源），
   在新版顶部单列「本次修订 / 更正」说明改了什么、为什么改。

### 选题池已经脚本化（2026-09-30 起，别再手排 HTML）

选题池的抓取是机械的、介绍文案是人写的，所以拆成两个脚本 + 一个文案文件：

```bash
# 变量取法见文末「环境」章节；路径随设备变化，**不要写死**
PY=<Python 解释器实际路径>
S=<本 skill 目录>/scripts
W=<工作目录>

# 1) 榜单（增量口径）
"$PY" "$S/github_trending_official.py" --period weekly --limit 20 --json --out "$W/_gh_weekly.json"
"$PY" "$S/github_trending_official.py" --period daily  --limit 20 --json --out "$W/_gh_daily.json"

# 2) 仓库字段（星标 / pushed_at 最后更新 / 许可证）—— 只抓要展示的，未抓的留「—」
"$PY" "$S/fetch_repo_fields.py" --repos-file <repo列表.txt> --out "$W/_gh_fields.json"

# 3) 拼版（文案写在 <工作目录>/_pool_desc.json，形状见 references/pool-data.sample.json）
# ⚠️ --out 只认最后一个，输出两个平台必须跑两次（2026-10-06 实测）
"$PY" "$S/build_pool.py" --work "$W" --out "<小红书成品根目录>/选题" --date YYYY-MM-DD
"$PY" "$S/build_pool.py" --work "$W" --out "<抖音成品根目录>/选题" --date YYYY-MM-DD
```

- **`build_pool.py` 只负责拼版**，不猜数据。它读 `_gh_daily.json` / `_gh_weekly.json` /
  `_gh_fields.json` / `_pool_desc.json`，输出 A 周榜 + A2 日榜 + B1/B2/B3 + 挑选建议。
- **兜底值不能是 0。** 脚本里 `stars()` 的逻辑是：优先 API 实时值 → 抓不到的退回
  trending 页总星快照 → 都没有才留「—」。2026-09-30 手写版曾因兜底写死 `0`
  导致周榜第 6–18 条全显示「总星 0」，交付前务必查一遍零值计数应为 0。
- 「最后更新」只对**抓过 API 的仓库**给值，其余留「—」，并在表下写明「未抓的不填，不猜」。
- 超过 60 天没推代码的打 `久未更新 N 天` 红标。
- 交付前做一次结构自检：行数应等于 `各表条数 + thead 行数`，`零值 = 0`。

### 项目页的四件套（一页一个项目时，页内固定这四块）

2026-09-29 用户明确：「一页一个项目，除了现有内容，说明可以应用到哪个地方、有哪些实例」。
四块**顺序固定、标签固定**，这样跨页读起来像同一套模板：

| 标签 | 回答什么 | 素材来源 |
|---|---|---|
| **能给什么** | 它到底做了什么（机制 / 能力，不写营销话） | 官方 README 的功能段 |
| **用在哪** | 具体场景。**必须来自官方 README 里的用例 / 目标读者段**，不要自己编场景 | README 的 Use Cases / Quickstart / 定位句 |
| **有啥实例** | 演示视频、示例图、论文、benchmark、可跑的 demo 命令、认证路径——**至少一项具体的** | README 里的 GIF / 截图 / 论文链接 / demo 命令 |
| **上手门槛** | 装什么、什么系统、要不要账号、要不要钱、许可证 | README 的安装段 + GitHub API 的 license 字段 |

**页内另需两行元信息**（放在大标题下面，正文之前）：
一行是 `owner/repo · 语言 · 许可证 · 本周 +N（总 M）`，一行是一句话定位。
**「本周 +N」要重复出现在项目页上**——读者可能从中间翻进来，一页必须能独立成立。

**若某块确实查不到**（README 里没有用例、也没有示例图）：
先把「能给什么」扩写到 3–4 句，补上**模块 / 引擎 / 支持范围**这类可核查的细节，
**再**考虑压缩。**不要用编造的场景填空。**

### 榜单页的容量规则

卡片可用高度 929px。按 5–10 条的正常行高（每行约 100–120px）一页装得下；
若某天坚持要放更多：

| 该榜条目数 | 做法 |
|---|---|
| **≤ 10 条（默认）** | 一页装完，行高宽松 |
| 11–20 条 | 一页装完，行高收到约 60px |
| 21–40 条 | 拆两页，页码标 `榜单 1/2`、`榜单 2/2` |
| > 40 条 | **先问用户**：拆多篇 / 只做 Top N。**不要静默丢条目** |

条目数由官方页决定、且**日榜每天条数不固定**（实测有 8 条的日子）。
**先抓数据、再算页数，不要凭经验预设。**

     不要写「想要完整地址的，评论区说一声」这类解释性长句，更**不用「私信发你」**
     （私信导流同样受限，且更易被判营销）。
   - 小红书与抖音均不允许站外链接导流。**这是平台通行规则的认知，本轮未在真实账号实测**——
     如实标注，别把判断说成验证结果。稳妥起见可先小号发一条观察 24 小时流量。

### 核查要严，文案要轻（2026-09-29 用户明确）

用户原话：「求证要严谨，但是图文没必要太诚实，没犯大错误就行，这类正常就不会有独立机构测试。
提醒弱字提示吧」

**两件事必须分开：**

| | 内部（`meta` 的 `verify` / `sources`） | 图上文案 |
|---|---|---|
| 标准 | **照样严格**：几手来源、有没有反证、哪里没查到，逐条写清 | **不做自我否定**，不主动交代「我没查到什么」 |
| 例 | 「独立机构横向评测：sources=0，本轮未找到，故不写『碾压』类结论」← **保留** | 图上不写「我没找到独立机构的横向评测」← **删掉** |

**为什么不写**：小众工具正常就不会有独立机构评测，写出来读者只会觉得「这东西没人验证过」，
是**自我削弱**，不是诚实。核查的价值在于**自己不说过头话**（不吹「最强」「碾压」），
不在于把查证过程的缺口贴到墙上。**没犯大错误就行。**

**提醒分两档：**

- **橙色提醒框（`.warn`）**——只留给读者**照着做会吃亏**的信息。
  例：repo 有近 6,000 个 open issues、某功能只对单一模型标定、有更成熟的替代品。
- **弱字（`.note-weak`）**——实用但不必警醒的补充说明。
  例：「图鉴示例图为作者生成，换模型效果不会完全一样」。
  灰色小字、无底色无边框，跟在正文后面即可。

```css
.note-weak{font-size:24px;line-height:1.62;color:#9A93B0;letter-spacing:.3px}   /* 小红书 */
.note-weak{font-size:25px;line-height:1.62;color:#9A93B0;letter-spacing:.3px}   /* 抖音 */
```

**删掉提醒框后必须重算填充度**（见踩坑第 7 条）。
实测：证据页 `gap` 小红书 42→82、抖音 54→96，才把留白补回 20% 左右。

### 踩到的坑（都已在 `templates` 用法里规避）

1. **提醒框（`.warn`）必须放在 `.in-items` 内部。**
   放在外面时，`.in-items{flex:1}` 会把它顶到页面底部，
   中间留出一大片空白——实测抖音「实例认证」页空白达 45%，成品像没做完。
2. **提醒框内容过长会溢出，并与 `.in-foot` 重叠。**
   实测周榜第 4 页出现「提醒文字压在页脚上」。
   修法两条同时上：给 `.in-items` 加 `padding-bottom:92px`（页脚是绝对定位的，
   内页 `padding-bottom` 只有 92px 不够），并把提醒裁到 3 行以内。
3. **抖音大字版比小红书版多占约 15–20% 高度。**
   同一段内容，内页标题 62px → **68px**、条目 33 → **36**、正文 29 → **31** 之后会溢出。
   要么每页少一条，要么把每条压到 2 行。
4. **末页（内容少）用 `justify-content:center`。**
   只有 2–3 条时，默认 `flex-start` 会让底部空掉一大半；
   居中是这种页面的正解，不必硬灌内容。
5. **同一个 cards.html 的改动必须串行提交。**
   （这条是 `article-to-social` 的既有教训，本次继续生效）
   对同一文件并行发多个 Edit，只有一处生效，其余被静默覆盖且都返回「成功」。
   **改动多时直接用 Write 整体重写，比分多次 Edit 安全。**
6. **末页 `.in-foot` 的左右两栏各写短句。**
   实测抖音末页左侧写「GitHub 搜 handraw-style ｜ 主技能 handdraw-style-prompter」，
   超宽换行后整块页脚被顶高、压到内容区。
   修法：左栏只放项目名就够（技能名本来也不该出现在读者文案里）。
7. **加内容后要重新算填充度。** 抖音内页正文 31px，`gap` 每加 10px 约多占 20px 高度。
   实测门槛页由 3 条拆成 4 条 + `gap` 50→60 后，留白从 44% 降到 25%——
   留白超过 35% 就看着像没做完，低于 10% 则发闷。
8. **长标题会换行，换行就把下面的内容挤出去。**（2026-09-29 改「一页一个项目」时踩到）
   实测项目页标题 `#5 ai-engineering-from-scratch` 在 62px 下折成两行，
   多出 76px，直接把末页的 `.in-foot` 顶穿（页脚压在第 4 块文案上）。
   修法：给这类长名加一个 `.in-title.sm{font-size:48px;line-height:1.3}` 保持单行，
   而不是把内容删掉。
9. **项目页内容长度不齐 → 用 `justify-content:center` 而不是 `space-between`。**
   一页一个项目后，各页文字量天然不等（hindsight 满、VoiceStudio 空）。
   `space-between` 会让短页的块间距被撑到 140px 以上、看着散架；
   居中则上下留白均等，短页只是「更透气」。**间距保持在 36–44px 即可。**
10. **两行页脚要预留 `padding-bottom:118px`。**
    末页若在 `.in-foot` 下面再挂一行补充说明（`.soft`，绝对定位 `bottom:30px`），
    页脚整体占高约 110px；`.in-items` 的 `padding-bottom` 只给 16px 必定撞车。

## 常见坑（均为实测）

1. **`IncompleteRead` 是常态。** 抓 trending 页会连续多次失败在同一字节数上。
   脚本已内置：`Accept-Encoding: identity` + 校验响应含 `</html>` + 重试 5 次退避。
   **不校验 `</html>` 会拿到被截断的 HTML——表格少几行而脚本不报错。**
2. **页面结构（改版时按此校准选择器）**
   - 条目块 `<article class="Box-row">`
   - 描述类名是 `col-9 color-fg-muted my-1 tmp-pr-4`，写 `pr-4` 匹配不到、描述全空
   - 星数 / fork 数在 anchor 内 **`</svg>` 之后、`</a>` 之前**，取该 anchor 内**最后一个**数字串
   - 增量 `([\d,]+)\s+stars\s+(today|this week|this month)`
3. **日榜条目数不固定。** 2026-09-29 当天只有 **8 条**（页面完整、`</html>` 收尾，
   WebFetch 与本地脚本两条独立路径读数一致）。不要以为是解析漏了，也不要补位。
4. **控制台编码会毁掉输出。** PowerShell 的 `*>` 重定向按 OEM 代码页解码，
   UTF-8 输出变乱码。**一律用 `--out`。**
5. **PowerShell 里别用 `"$b\$f`_u8.txt"` 这种拼接。** 反引号 + `$f` 会被解析器
   判成 `%VAR%` 形态并直接拦下报「cmd.exe %VAR% environment variable syntax」。
   用 `Join-Path` 拼路径。
6. **同一个项目可能挂在多个榜上**，周榜篇不能照抄日榜篇的文案，
   封面钩子也要分「今天 / 这一周」。
