## 五条铁律（先记住）

1. **方向 A：一个榜 = 一篇。** 日榜、周榜**各自独立成篇**，不混排。
2. **方向 B：一个项目 = 一篇。** 不在一篇里横评多个项目。
3. **方向 A：只取前 5 条或前 10 条**（2026-09-29 用户明确）。
   不搬整榜，也不需要那个「一页 20 行」的紧凑版式。
4. **方向 A：第 2 页起「一页一个项目」**（2026-09-29 用户明确）。
   每页固定四件套：**能给什么 · 用在哪 · 有啥实例 · 上手门槛**。
   用户原话：「后面的每一页，希望做到『一页一个项目』。除了现有内容，
   你可以看一下可以应用到哪个地方，以及有哪些实例。」
5. **方向 B：必须放真图，不许光写文字**（2026-09-29 用户明确）。
   封面用实例图做视觉主体，另设一页「实例」放整页成品图。
   图优先**自己实跑生成**；退而求其次才用官方实测样图，且必须标注来源。
   用户原话：「我希望能够直接在图文里面展示实例……可以直接用 skill 做成封面，
   或者你那不是有官方实测的内容吗，或者正文。」

**封面一律不写日期**（2026-09-29 用户明确，两条方向都适用）：
「我可能会提前做。」日期只放正文、页脚与 meta 的 `date` 字段。

平台图片上限：**小红书 18 张 / 抖音 35 张**（用户 2026-09-29 明确给出）。

## §A 榜单型（选题方向 A：GitHub 日榜 / 周榜）

### 用户原话对应的五条硬要求

1. **第一页就直接展示总榜单**（不是先讲意义再上榜单）
2. 后面的图文页，展示**项目名称**以及**它能给我们带来什么**，做**简单介绍**
3. 日榜和周榜**相当于是两条图文**，不混在一起
4. **只取前 5 或前 10 条**（2026-09-29 新增）
5. **第 2 页起一页一个项目**，每页补上**应用场景**与**实例**（2026-09-29 新增）

> 原第 3 条「把所有的榜单内容都写出来」被第 4 条限定为：**写全你取的那 5 / 10 条**，
> 而不是写全整榜。取几条就在榜单页列几条、逐项页讲几条，**数量必须对齐**。

### 项目页的固定骨架（P3 起，每页相同）

```
[页眉]   GitHub 周榜 | 一页一个项目                       [页码 02…06]
[大标题] #1 hindsight
[元信息] vectorize-io/hindsight · Python · MIT · 本周 +15,537（总 41,002）
[副标题] 会自己学习的 Agent 记忆系统
[短分隔线]
能给什么   ← 机制 / 能力，落到具体动作或结果，不写营销话
用在哪     ← 应用场景，**必须来自官方 README 的用例 / 目标读者段**
有啥实例   ← 演示视频 / 示例图 / 论文 / benchmark / demo 命令 / 认证路径，至少一项具体
上手门槛   ← 装什么 / 什么系统 / 要不要账号 / 要不要钱 / 许可证
```

**排版规则**：
- 左侧标签固定 **120px** 宽、品牌蓝加粗；右侧正文 `flex:1`，27px / 行高 1.68。
- **四块的顺序不许变**——跨页读起来才像同一套模板。
- **「本周 +N」要在项目页上重复一次**。读者可能从中间翻进来，一页必须能独立成立。
- 元信息里带上 `语言 · 许可证`，这两项都取自 GitHub API，是可核查的硬信息。

> 填充度：一页一个项目后各页文字量天然不等。
> **用 `justify-content:center` 让内容块垂直居中**，间距保持 36–44px。
> 实测：hindsight 页顶底各留约 60px、VoiceStudio 页各约 130px，都不难看；
> 若改用 `space-between`，短页的块间距会被撑到 140px 以上，反而散架。
> **短页不要去灌水**——想加内容就加真内容（见下条）。

### 某块查不到素材时怎么办

用户明确：「如果确实没有，就将介绍内容再拓展一些，反正做到一页一个项目就可以了。」

处理顺序（**不许跳步**）：

1. 先把 README 全文下载核对。**本 skill 的抓取脚本默认只取约 12KB，容易被截断**——
   实测 hindsight 从 12KB 截到 25KB、paperclip 13KB 截到 30KB，
   `## Use Cases` 段整段丢失。改用
   `raw.githubusercontent.com/<owner>/<repo>/<branch>/README.md` 重抓一次
   （分支名先试 `main`、再试 `master`）。
2. 从「能给什么」扩写：补**模块名 / 引擎 / 支持范围 / 阶段数 / 语言数**这类可核查细节。
3. 从 README 的 Use Cases / Quickstart / 定位句里提炼「用在哪」。
4. 从 README 的 GIF、截图、论文链接、demo 命令里挑「有啥实例」。
5. **仍不足就让它短一点**（居中留白），**绝不用编造的场景填空**。

### 日榜篇与周榜篇必须互相区分

同一项目可能同时挂在两个榜上（2026-09-29 实测：日榜第 1 `debpalash/VoiceStudio`
也出现在周榜）。**周榜篇里同一项目的介绍文案不能照抄日榜篇**，至少换一个切入角度。

封面钩子口径也要分开：日榜说**今天**、周榜说**这一周**。
封面上的「周期」字样必须与榜单口径一致，否则读者会当成重复内容。

### 项目页每块的写法

「能给什么」是核心，必须落到具体动作或结果，例如
「把 3 小时的会议录音转成带说话人标注的文字稿，本地跑不联网」，
而不是「提升工作效率」。

> 2026-09-29 实测：每块正文控制在 **3–4 行（约 75–110 字）**；
> 四块加起来一页填充度约 70–80%，居中排布后观感稳定。

## §B 推荐型（选题方向 B：好用的项目 / 工具 · 一个项目一篇）

用户原话：「首页需要吸引人点进来，可以设置一个钩子或展示它最好的卖点，
形式跟抖音、小红书差不多。后续分页再去详细介绍项目背景、能够做什么、实例认证等。」

### 两平台不是「同一篇换个皮」

用户明确要求「**需要确认抖音和小红书有不同的逻辑**」。同一份素材：

- **小红书是「读」** —— 读者按顺序看完，为**收藏**而读
- **抖音是「划」** —— 读者可能从**任意一张**滑入，为**划到最后一张**而划

| 维度 | 小红书版 | 抖音版 |
|---|---|---|
| 一页的目的 | 承接上文叙事 | **必须独立成立**，脱离上下文也能看懂 |
| **第 2 页** | 承接封面往下讲 | **决定他要不要划第 3 张**；若只是封面的补充说明，这条就到头了 |
| 页序 | 按叙事顺序 | **排序本身就是核心工作** |
| 内页字号 | 标题 62 / 条目 33 / 正文 29px | **68 / 36 / 31px**（大字版） |
| 文案 | **标题 ≤20 字、正文 ≤1000 字**（**硬规则**，目标 600–900）；**必须用 emoji 做小标题分段** | **首行即标题 ≤20 字、正文 ≤1000 字**——**与左侧完全同口径，同为硬规则**（2026-09-29 用户最终更正：「两边都是标题 20 字，正文 1000 字」）；**同样用 emoji 分段** |
| 话题 | 5–8 个：行业词 → 产品词 → 场景词 | **三级结构**：泛流量 + 垂直 + 地域/热点 |
| 合规 | 无强制标注 | **「内容由 AI 生成」标注项：AI 不代操作**（保持页面默认状态，勾不勾由用户本人决定） |
| 末页 | 来源一行 | 来源 + **互动引导**（评论权重高，要埋争议点） |
| 特有元素 | — | **连号页码** `01/07`、封面底部**滑动提示** |

**一句话：小红书版改的是文案，抖音版改的是页序。**

### 封面钩子的三种写法（两平台通用，选一，与 article-to-social 标题候选规则一致）

- **数字型**：「280 种手绘风格 + 122 种版式，24 天涨了 3,588 星」
- **冲突型**：「ElevenLabs 收钱做的事，它本地免费干完了」
- **场景型**：「写论文配图烦？有人把 280 种手绘风格打包成了技能包」

## 实测修正（2026-09-29 第一批成品跑完后补）

这四条是**渲染后肉眼复核才发现的**，写蓝图时想不到：

1. **提醒框（`.warn`）必须放进 `.in-items` 内部。**
   放外面会被 `flex:1` 顶到页面底部，中间空一大块（实测抖音「实例认证」页空白 45%）。
2. **提醒框 + 长内容会溢出，压到 `.in-foot` 上**（实测周榜 P4）。
   修法：`.in-items` 加 `padding-bottom:92px`，同时把提醒裁到 3 行内。
   内页自带的 `padding-bottom:92px` **不足以**避开绝对定位的页脚。
3. **抖音大字版（68/36/31）比小红书版（62/33/29）多占约 15–20% 高度。**
   同一段文案直接搬会溢出。要么每页少一条，要么每条压到 2 行。
4. **末页只有 2–3 条时用 `justify-content:center`**，
   否则底部空一大半。这是这种页面的正解，不要为填满而灌水。
5. **「上图下文」比「图上压字」稳。**
   实测连踩三次：图与文字区块之间必须留 **≥60px** 余量，
   第一次只差 2.4px，视觉上就是文字贴在图上。
   - 封面：**图区 1080×1080 + 深色标题区 360px**（图 `object-position:center 100%`，
     底部对齐才能把内容区完整装进 1080 高度）
   - 实例页：**说明在上（`top:106px`）+ 图在下（`top:210px`）**
6. **AI 生图原图右下角带平台水印，发布前必须裁掉。**
   别凭感觉设 `object-position`——先用像素探针扫出**内容下边界**（实测 y=1208，
   该行之后全是空白），再裁到那一行。裁切用 Chromium 截图完成，不必装 Pillow / sharp。
   工具见文末「配套小工具」。
7. **长项目名会把标题挤成两行，两行就把页脚顶穿。**
   实测 `#5 ai-engineering-from-scratch` 在 62px 下折行，多占 76px，
   直接压到末页的 `.in-foot` 上。修法：加 `.in-title.sm{font-size:48px;line-height:1.3}`
   保持单行，**不要为了排版删内容**。宽度估算用 `0.55em/拉丁字符 + 1em/汉字`。
8. **项目页文字量天然不齐 → 用 `justify-content:center`，不要用 `space-between`。**
   实测 `space-between` 会把短页的块间距撑到 140px 以上，看着散架；
   居中后 hindsight 页顶底各留约 60px、VoiceStudio 页各约 130px，都自然。
   间距保持 36–44px。
9. **两行页脚要预留 `padding-bottom:118px`。**
   末页若在 `.in-foot` 下再挂一行 `.soft`（绝对定位 `bottom:30px`），
   页脚整体占高约 110px；`padding-bottom` 只给 16px 必定撞车。

**填充度参考（实测）**：point 结构 5 条 × 3 行 ≈ 81%；
item 结构 3 条 × 4 行 ≈ 81%；item 结构 2 条 + 提醒框 ≈ 83%；

## 配套小工具（2026-09-29 新增，已落位到本 skill 的 `scripts/`）

| 工具 | 做什么 | 用法 |
|---|---|---|
| `crop.cjs` | 用 Chromium 把图裁成指定尺寸，**不依赖 Pillow / sharp** | `node crop.cjs <源图> <输出> <宽> <高> [offsetY] [scale]` |
| `probe_png.cjs` | canvas 读像素，定位**内容下边界**与右下角水印范围 | `node probe_png.cjs <图> [右侧占比] [起扫比例] [阈值]` |

两个都通过 `NODE_PATH` 找 `playwright-core`，Chromium 从 `%LOCALAPPDATA%\ms-playwright\` 自动扫。
`probe_png.cjs` 会打印 `LOWEST_CONTENT_ROW`——**裁图就裁到这一行**。

典型用法（裁掉 AI 生图右下角水印）：

```bash
export NODE_PATH="C:/Users/<you>/.workbuddy/binaries/node/workspace/node_modules"
node probe_png.cjs gen/raw.png 0.0 0.72 45      # 先问：内容到哪一行结束
node crop.cjs      gen/raw.png gen/clean.png 1024 1210 0 1   # 再裁到那一行
```
